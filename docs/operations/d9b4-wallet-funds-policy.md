# D9-B-4 资金场景、规则配置与停运处置

## 1. 固定边界

- P1 钱包币种只有 `CNY`，金额始终为整数分并在服务层使用 `BigInt`；任何其它币种失败关闭。
- 余额永不过期。配置保留 `balanceExpiration`，当前数据库 enum 和请求 schema 唯一允许值均为
  `never`；本切片没有余额过期任务、字段或留桩。
- 财务日切固定为 `Asia/Shanghai`。服务端账单只有这一种时间口径，跨时区展示由客户端负责。
- 规则保存在版本化的 `walletPolicyVersions`，`walletPolicyHeads` 通过单行 CAS 指向当前版本；版本不可
  更新或删除，每次变更只允许 active `system_admin`，并追加 `wallet.policy.updated` 审计。没有新增生产
  必需环境变量。
- 本切片不接入第四 ledger，不新增审批角色或工作流，不新增通知 outbox，也没有管理员批量退款入口。

## 2. 九项可管理规则

| 规则                      | P1 默认/允许值                                             | 执行语义                                                                                                  |
| ------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 币种                      | `CNY`，唯一允许值                                          | 充值、消费、退款、追回和账单均拒绝其它币种                                                                |
| 余额是否过期              | `never`，唯一允许值                                        | 不实现过期逻辑                                                                                            |
| 单次充值上限              | `5,000,000` 分                                             | 创建充值单前校验，支付确认入账时再校验账户上限                                                            |
| 账户余额上限              | `10,000,000` 分                                            | 同事务锁定账户并从追加式账本推导 posted 后校验，不读缓存余额                                              |
| 单笔消费上限              | `3,000,000` 分                                             | 交互式余额支付和获准的紧急续费在 hold 前分别校验                                                          |
| 争议/异常退款后允许负余额 | `true`                                                     | 仅支付退款/争议追回可产生负数；普通 hold/capture 永不透支                                                 |
| 受限账户用于紧急续费      | `false`                                                    | 开启时也只允许唯一限制为 `balance_spend_disabled` 且存在有效 `renewalMandate` 的无人值守续费              |
| 财务日切时区              | `Asia/Shanghai`，唯一允许值                                | 本地自然日转换为 `[00:00, 次日 00:00)` 的 UTC 区间                                                        |
| 账单与期初期末计算        | `ledger_entries_start_inclusive_end_exclusive`，唯一允许值 | 期初为开始前全部 entry 推导值；期末为结束前全部 entry 推导值；区间 entry 为 start-inclusive/end-exclusive |

规则版本还要求：三个金额上限均为正整数；账户上限处于 JavaScript/PostgreSQL 安全整数范围；单次充值和
单笔消费均不得高于账户上限。Zod、数据库 CHECK 与运行时资金调用点分别失败关闭。

## 3. 资金场景

### 3.1 重复充值

只有两个不同充值单同时满足同一 customer、同一 wallet account、同一冻结金额、同一币种、均已由主动
查单确认并各有独立微信交易号和 B-1 credit 事实时，后一个充值单才被视为重复充值。退款金额只读重复
充值单的冻结金额。退款复用 D5-04 微信原路退款和 B-1 hold/capture；充值单 CAS、退款目标唯一索引及
provider refund 幂等键保证 N 路请求只创建一次退款、只扣回一次余额，原充值 credit 不会重复追加。

### 3.2 平台未提供服务

订单退款只读取 `orders.paymentChannel`：`balance` 走 B-3 余额释放/退回，`native`/`h5` 走 D5-04 微信
原路退款。不得从微信交易号、商户单号或其它间接信号推断渠道；金额只读取订单冻结金额。状态不明保持
现状并进入既有人工复核，不自动重复提交 provider 写请求。

### 3.3 账号关闭

A6 的正余额注销阻塞保持不变。持有精确 active closure request 的系统执行器可按最近充值优先，对当前
未消费余额逐笔发起原路退款；部分消费的充值只退剩余可用金额，不没收、不清零、不转入平台账户。发起
退款后正余额可变为 hold，但 `refund_or_reconciliation_issue` 继续阻塞；只有 provider 成功、B-1 capture
完成且余额归零后，注销前置检查才可继续。

### 3.4 充值支付退款或争议

支付平台对已入账充值发生退款或争议时，系统以唯一 recovery key 在同一事务认领 `credited` 充值单，先
核验独立 B-1 credit 事实，再追加 `recovery` transaction/entry。若余额已经消费，允许 posted/available
转负；这条路径是唯一可产生负余额的路径。负余额产生后，立即复用 A3 对 customer 施加
`balance_spend_disabled`、追加人工复核和审计。普通消费仍由 B-1 原子 available 谓词拒绝透支。

## 4. 平台停止运营处置

本节定义责任和顺序，不提供批量退款工具，也不替代 B-5 审批或 B-6 第四 ledger。

1. 事件负责人先停止新充值、新余额消费和新履约入口，保留查询、账单导出、provider 查单和审计读取；
   不删除或改写任何 wallet entry。
2. 财务负责人按 `Asia/Shanghai` 固定日切导出每个账户的期初、区间 entry 和期末，使用追加式账本重算
   posted/held/available；对 hold、unknown、退款中和争议记录逐项列出，不以展示余额作真源。
3. 支付负责人用既有微信查单/退款查询核对每笔可原路退回的充值；状态未知只查询，不重提。余额支付订单
   继续按其订单渠道处理，禁止与微信路径互串。
4. 客服/合规负责人联系用户并记录处理依据。每个用户按未消费充值来源逐笔走既有原路退款；不能自动
   判断或退款失败的记录进入既有 `ManualReviews`，不得清零或转入平台账户。
5. 安全负责人保全规则版本、审计、账本和 provider request id；财务负责人复核每个账户最终余额及所有
   pending/unknown 项。只有余额为零且无退款/对账阻塞时，才可继续账户关闭或最终数据保留流程。

当前账本的 credit/hold/capture/release/recovery 事实、不可变快照和上海日切账单足以表达上述逐账户处置；
本切片没有实现管理员批量执行、第四 ledger 自动对账或生产操作按钮。

## 5. A4 风险分级逐项对照

| 本切片操作         | A4 档位/既有授权                              | 结论                                                              |
| ------------------ | --------------------------------------------- | ----------------------------------------------------------------- |
| 交互式余额消费     | `balance_spend` step-up                       | B-3 入口保持不变；B-4 仅在其后增加单笔消费上限                    |
| 账号关闭前余额退款 | 注销申请 step-up + 冷静期；后续为受信系统执行 | 精确 active A6 request key 才能发起；不另建 grant                 |
| 无人值守紧急续费   | 有效 `renewalMandate`，不得依赖 step-up       | 仅配置允许且 A3 唯一限制为 `balance_spend_disabled` 时放行        |
| 重复充值退款       | 受信系统资金处置，不是用户交互操作            | 复用 D5-04、B-1、审计和幂等；不降低任何交互式档位                 |
| 未提供服务退款     | 受信履约/退款任务                             | 只读 `paymentChannel`，沿 B-3/D5-04 既有路径                      |
| 支付退款/争议追回  | provider/受信系统事件                         | 不使用交互式 step-up；负余额后立即施加 A3 限制并人工复核          |
| 资金规则变更       | active `system_admin` + 版本化审计            | A4 表未定义用户 step-up；B-5 审批尚未实现，未提前留桩             |
| 账单导出           | 当前 customer session + owner scope + 审计    | 只读操作，不提升为余额消费档                                      |
| 平台停运处置       | 运维规则，无批量执行入口                      | 每笔退款仍使用上述既有档位；未来管理员批量入口必须由 B-5 另行设计 |

A4 表中 DNS、域名锁、实名、管理密码和找回/换绑冷静期均不由本切片修改。余额消费与注销两行继续沿用
既有保护；没有遗漏或降级本切片触达的操作。
