# 内容发布 Runbook

本 Runbook 适用于 Payload Admin 中的文章 `articles`、专题 `topics`、TLD 页面 `tldPages` 和帮助页 `helpPages`。首批内容应先使用[内容模板](content-templates/README.md)完成字段和来源检查。

## 1. 权限与不可绕过边界

- 只有 active 且已完成密码 + TOTP 的 `content_editor` 或 `system_admin` 可以创建、编辑、预览和执行内容工作流。
- Payload 原生发布、取消发布和定时发布入口已关闭。只能使用文档页顶部的“提交审核”“立即发布”“定时发布”“取消定时”“发布修订”“下线”“归档”。
- 保存、自动保存或直接修改字段不会发布内容；工作流状态、计划时间、发布时间和修订人由服务端维护。
- 预览地址是私有的，返回 `noindex, nofollow` 和私有禁缓存头。不要把预览 URL 当公开链接分享。
- 发布前 `source` 必须非空，正文必须通过受控富文本清洗，所有图片必须是有权限读取的站内 Media 图片。

## 2. 状态流转

```text
draft --提交审核--> in_review --立即发布/定时任务到时--> published
                                published --发布修订--> published
                                published --下线--> unpublished
                                unpublished --归档--> archived

in_review --定时发布--> in_review + scheduledPublishAt
in_review + scheduledPublishAt --取消定时--> in_review
```

| 当前状态      | 允许操作                                               | 结果与公开影响                                                             |
| ------------- | ------------------------------------------------------ | -------------------------------------------------------------------------- |
| `draft`       | 编辑、预览、提交审核                                   | 普通用户访问 404，不进入 sitemap。                                         |
| `in_review`   | 编辑、预览、立即发布、定时发布；有计划时还可取消或改期 | 仍未公开；定时不是新状态。没有“退回草稿”操作，审核修改直接在当前记录完成。 |
| `published`   | 保存草稿修订、预览、发布修订、下线                     | 保存修订不会替换线上版本；“发布修订”才切换公开版本。                       |
| `unpublished` | 编辑、预览、归档                                       | 公开页为 404，不能重新提交审核或重新发布。                                 |
| `archived`    | 只读预览                                               | 永久退出工作流；不能编辑、恢复或重新发布。                                 |

所有未定义迁移都应停止处理，不要尝试用通用 REST、Local API、原生 Payload 按钮或直接字段编辑绕过状态机。

## 3. 草稿到发布

### 3.1 创建与编辑草稿

1. 在对应 Collection 新建记录，使用相应[内容模板](content-templates/README.md)。
2. 填写 `title`、稳定 `slug`、`summary`、`content` 和 `source`；配置适用的分类、标签和关联。
3. 按模板确认 `meta.title`、`meta.description`、`meta.image`、`meta.canonical` 和 `meta.noIndex`。canonical 默认留空，`noIndex` 默认关闭。
4. 等待自动保存结束。页面仍显示有未保存修改时，不执行工作流操作。
5. 打开“预览”，检查标题层级、来源、更新时间、图片、链接、相关内容、SEO/商业标识和移动端布局。

### 3.2 提交审核

1. 清除全部模板占位符和空章节，完成模板中的提交审核前检查。
2. 点击“提交审核”，确认状态从 `draft` 变为 `in_review`。
3. 审核人再次预览并核对：事实与来源、转载授权、赞助披露、SEO、canonical、收录开关、关联目标和敏感信息。
4. 审核中发现问题时直接编辑并等待自动保存；当前系统没有 `in_review → draft` 操作。

### 3.3 立即发布

1. 确认页面无未保存修改，状态为 `in_review`，`source` 完整。
2. 点击“立即发布”，确认状态为 `published`，计划时间已清空。
3. 使用无管理员会话的浏览器访问公开路径，确认 HTTP 200、标题、来源、图片、关联、canonical 和 robots 正确。
4. 请求 `/sitemap.xml`：当 `noIndex=false` 且 canonical 指向自身时，应出现该页面；自定义 canonical 指向别页或 `noIndex=true` 时不应出现。
5. 检查审计记录中存在对应状态变化，记录发布日期和核验人。

### 3.4 发布已上线内容的修订

1. 在 `published` 记录上编辑。自动保存只产生草稿修订，旧公开版本继续服务。
2. 在私有预览检查新版本，并在正文“修订记录”写明日期、编辑、变化和依据。
3. 等待自动保存完成后点击“发布修订”。不要点击“下线”来发布普通修正。
4. 重新核验公开页、sitemap、canonical、关联和审计记录。

## 4. 定时发布、改期与取消

### 4.1 新建计划

1. 内容必须处于 `in_review` 且已完成发布检查。
2. 在“定时发布时间”输入框选择未来时间。该控件使用操作者浏览器的本地时区，提交时转换为 ISO 时间；跨时区协作时在审核记录中同时写明本地时间、时区和 UTC 时间。
3. 点击“定时发布”，刷新后核对页面显示的计划时间。
4. 到时后由独立 `publishing` Worker 执行发布。安排值守人在计划时间后核对公开页、sitemap 和审计记录，不要只以 Job 已创建判断成功。

### 4.2 直接改期

1. 保持状态 `in_review`，输入新的未来时间并再次点击“定时发布”。
2. 刷新并确认 `scheduledPublishAt` 已更新为新时间。
3. 旧 Job 不会被物理删除，但到时会因计划时间不匹配而安全忽略；不要手工删除或重放它。

### 4.3 取消定时

1. 在仍为 `in_review` 且显示计划时间时点击“取消定时”。
2. 确认状态仍为 `in_review`，计划时间已清空，公开路径仍为 404。
3. 已排队 Job 会保留，但执行时因计划不存在而安全忽略。取消后若要发布，重新审核并选择立即发布或新时间。

### 4.4 计划时间已过但未发布

1. 确认页面仍是 `in_review`，不要反复点击定时发布或直接操作 Job。
2. 记录内容类型、文档 ID、计划时间、操作者和 traceId；由 `system_admin` 检查 `publishing` Worker/Job 与调度人账号是否仍 active。
3. 若内容不应继续自动发布，先点击“取消定时”。故障排除后重新审核，再明确选择立即发布或新时间。

## 5. 下线与归档

### 5.1 下线前检查

1. 记录下线原因、负责人、时间和替代页面；在正文修订记录或受控运营记录中保留依据。
2. 检查指向该页的站内关联、导航、其他页面 canonical 和现有 Redirects。先准备必要替代内容，但替代页必须在建立引用型 301 前发布。
3. 对法律、安全、隐私或严重错误可优先下线；其他情况尽量先准备替代页，减少 404 窗口。

### 5.2 执行下线

1. 在 `published` 记录点击“下线”，确认状态变为 `unpublished`。
2. 使用匿名请求确认原公开路径返回 404。
3. 确认动态 sitemap 不再包含该页。搜索引擎已有索引不会瞬时消失，需等待其重新抓取。
4. 检查影响：
   - 公开关系读取会过滤该页；其他页面后台保存的关系仍存在，但不会公开展示它。
   - TLD 页反向相关内容会移除该项。
   - 如果这是某分类/标签最后一篇已发布文章，对应分类/标签公开页也会变为 404 并退出 sitemap。
   - 指向该记录的引用型 301 会在重定向缓存刷新后失效；最长可能短暂使用约 30 秒旧缓存，之后旧路径通常返回 404。
5. 检查审计记录和所有替代入口。

`unpublished` 没有返回 `in_review` 或 `published` 的合法迁移。不要把“下线”当临时隐藏开关。

### 5.3 归档

1. 只有确认内容不再恢复、证据和替代入口已记录后，才在 `unpublished` 记录点击“归档”。
2. 确认状态为 `archived`。归档不会产生新的公开影响：页面在下线时已经是 404 且不在 sitemap。
3. 归档记录只读，不能编辑、恢复或发布；仍可由有权限的管理员预览并通过版本/审计追溯。

## 6. 页面改址 301

### 6.1 正确做法

1. 确定旧路径和唯一最终目标。不要为了改标题而改 slug。
2. 若同一内容改 slug，在 `published` 记录保存新 slug 草稿并完成预览，然后点击“发布修订”，确认新路径 HTTP 200。
3. 立即在 Redirects 新建规则：
   - `from`：旧站内绝对路径，例如 `/articles/old-slug`；
   - `type`：只能选 `301`；
   - `to.type`：优先选 `reference`；
   - `to.reference`：选择已经发布的新目标记录。
4. 只有无法引用的固定站内页面才使用 `custom`，目标仍必须是干净的站内绝对路径。
5. 匿名验证旧路径返回 301，`Location` 指向预期新路径，并验证最终页面 200、canonical 指向自身、sitemap 只保留目标页面。
6. 更新所有可控站内链接，301 只用于兼容旧入口，不替代站内链接维护。运行时重定向索引缓存约 30 秒，变更后在缓存窗口结束后再做最终确认。

### 6.2 禁止事项

- 禁止目标为站外 URL、协议相对 URL、带反斜杠、凭据、查询参数或片段的 URL。
- 禁止覆盖 `/admin`、`/api`、`/go`、`/_next`、健康检查、robots、sitemap 等系统路径。
- 禁止起点等于终点、直接/间接循环、重复来源或超过 10 跳的链；应直接指向最终目标，避免链式改址。
- 禁止引用草稿、待审核、已下线或归档内容；分类/标签目标必须至少包含一篇已发布文章。
- 禁止用 canonical 代替改址。canonical 不产生跳转；把当前页 canonical 到别页还会让当前页退出 sitemap。
- 禁止先创建指向未发布目标的规则，也不要先下线旧页再慢慢准备目标。
- 规则不允许内置查询参数，但运行时会保留访问旧路径时已有的 query；不要把可能携带敏感 query 的入口设计为改址来源。

## 7. 回滚

### 7.1 草稿或待审核问题

- 继续编辑当前记录、清除错误、等待自动保存并重新预览。
- `in_review` 没有退回草稿动作；不需要也不得绕过状态机改 `workflowStatus`。

### 7.2 错误定时或计划不应继续

- 计划尚未执行：点击“取消定时”，确认时间清空，再修正或重新排期。
- 已直接改期：以页面当前 `scheduledPublishAt` 为准；旧 Job 会被忽略。
- 时间已过且状态不明：先取消剩余计划并按 4.4 节调查，不要重复运行 Job。

### 7.3 已发布修订有误，但无需紧急下线

1. 保持记录为 `published`，不要点击“下线”。旧版若仍正确，可从 Payload 版本历史恢复已知良好版本为草稿，或直接修正当前草稿。
2. 私有预览确认恢复内容，并新增修订记录。
3. 等待自动保存完成，点击“发布修订”。
4. 匿名核验公开页、SEO、sitemap、关联和审计。

### 7.4 必须紧急下线

1. 点击“下线”并确认公开 404、sitemap 移除和关联影响。
2. 当前记录不能重新发布。复制已知良好内容创建新记录，使用新 slug，重新执行 `draft → in_review → published`。
3. 新记录发布成功后建立旧路径到新记录的引用型 301，并更新站内链接。若业务必须保留原 slug，停止操作，由 `system_admin` 评估如何在完整审计下释放唯一 slug；不得直接改数据库。
4. 不要归档旧记录，直到替代页、301、审计和搜索影响全部确认。

### 7.5 错误 301

1. 目标错误但规则仍需要：内容管理员将目标更新为已发布的正确最终目标，确认没有循环或长链。
2. 规则完全不应存在：停止继续改址，由 `system_admin` 删除该规则；普通内容管理员没有删除权限。
3. 等待最多约 30 秒缓存刷新，再匿名核验旧路径、`Location`、最终状态和 query 行为。
4. 若错误跳转涉及安全、隐私或站外暴露，记录时间、路径、影响和审计事件并按安全事件流程升级。

## 8. 发布完成记录

每次发布、修订、下线、归档或改址至少记录：内容类型、文档 ID/slug、动作、操作者、审核人、时间与时区、来源/授权状态、修订或下线原因、公开验证结果、sitemap/robots/canonical 结果及相关 Redirect ID。审计日志是系统证据，正文修订记录和运营记录用于解释业务原因，二者不能互相替代。
