## 1. 审计结论

- 审计基线：`main@2353d4acd68e84e98546f365a39ad1f5bb7021d8`，冻结基线
  `P1-BASELINE-2026-08-18.1`。
- 模块结论：M01～M15 完全满足；M16 部分满足。M16 的服务、API、Collection 与集成测试已经覆盖
  域名资产、提醒、自动续费、Name Server 和 D9 域名控制台能力，但当前用户界面只提供资产列表、
  详情、同步和历史展示；Name Server 写入口被明确禁用，提醒偏好、主动/自动续费和 D9 域名控制台
  的用户写入口也未接入。因此 11.2“`M01～M16 全部实现并通过 PRD 验收`”保持未勾选。
- 静态扫描结论：发现 a 类生产零调用能力、完全零引用导出、平行反馈 Collection、直接冗余依赖和
  未接入当前流程的一次性脚本；没有可由计划中具体后续阶段承接的 b 类项。因此 11.2“不存在
  P1.5/P2/P3 空模块、未使用基础设施或越界功能”保持未勾选。
- 本文只记录事实和建议，不删除、不改写或接入任何业务代码。

## 2. 方法与判定口径

1. 逐字引用 `Wanmi.AI-产品需求文档-PRD.md:181-196` 的 P1 能力列，并继续检查同文档
   `6.1～6.16` 的详细验收约束；“实现位置”只列当前生产路径的代表性入口，不以测试夹具代替实现。
2. 验证证据只引用仓库中实际存在的既有 unit/integration/e2e/acceptance 用例。本文逐个核对了文件、
   行号和完整用例名；本切片是文档与审计档，不重跑代码测试，也没有为了凑证据新增重复测试。
3. 对 `apps/web/src/services`、`collections`、`app/api`、`components` 共 280 个 TypeScript/TSX 文件做
   import graph、TypeScript symbol、Next.js 文件路由、Payload Collection 注册、Payload 字符串组件
   注册和测试引用联合扫描。106 个 `route.ts` 是 Next.js 框架入口，不能因没有 TypeScript import
   就判死；Payload Collection 和字符串注册组件同理。
4. 导出扫描覆盖 `services`、`collections`、`components` 的 662 个运行时导出。先剔除同文件真实调用、
   re-export、Next.js/Payload 发现式入口和仅因测试从 HTTP/slug 进入而没有直接 symbol import 的误报；
   再单列完全零引用导出和仅由测试调用的生产能力。
5. 依赖扫描同时检查 TS/TSX import、CSS/PostCSS 配置、package scripts、编译器 ambient types 和
   `pnpm why` 的 peer/runtime 关系。设施扫描检查 `docker-compose.yml`、`deploy/`、根 `scripts/` 与
   `apps/web/scripts/` 是否被 Makefile、package scripts、CI、验证器或 Runbook 实际引用。
6. 分类固定为：a＝当前确实无生产用途/调用且计划无承接项，建议删除或在另一个批准切片决定接入；
   b＝计划中有明确未完成阶段承接；c＝实际由框架、配置、间接调用或测试链路使用，静态直接引用法漏报。
   计划只有“功能打磨后统一做前端”的原则性说明，没有任务、退出条件或里程碑，不能作为 b 类依据。
